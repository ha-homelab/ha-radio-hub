# RF transmitter startup guard

The RF package links this original MIT-licensed wrapper around `rmt_new_tx_channel`. It changes only the configured CC1101 transmitter GPIO. All other RMT allocations pass through unchanged. It does not modify ESPHome or the installed ESP-IDF SDK.

In ESP-IDF 5.5.5 the allocator establishes the RMT idle level, then connects/enables the pad, then enables the requested open-drain mode. ESPHome 2026.10.0 zero-initializes that idle level and only releases an open-drain pad after allocation/enabling. Meanwhile CC1101 GDO0 is still an output: its power-on clock or asynchronous RX signal. That creates a transient contention window.

The wrapper preloads the GPIO latch HIGH without enabling its output, sets open-drain mode, then calls the original allocator with a copied configuration whose `init_level` is HIGH. The first routed RMT state therefore releases GDO0. Errors stop allocation; unrelated channel settings and later TX/EOT behavior remain unchanged. A final validator pins the exact upstream transmitter SHA-256, ESPHome 2026.10.0, ESP-IDF 5.5.5 and ESP32/ESP32-S3; a compile guard independently rejects an SDK version change.

Sources: [ESP-IDF allocator](https://github.com/espressif/esp-idf/blob/v5.5.5/components/esp_driver_rmt/src/rmt_tx.c), [GPIO implementation](https://github.com/espressif/esp-idf/blob/v5.5.5/components/esp_driver_gpio/src/gpio.c), [ESPHome transmitter](https://github.com/esphome/esphome/blob/704551a6c93c29a311802f7ee97d67a9e9bce718/esphome/components/remote_transmitter/remote_transmitter_rmt.cpp), and [CC1101 datasheet](https://www.ti.com/lit/ds/symlink/cc1101.pdf), section 26.

Native tests compile the actual wrapper against an allocator double that models the IDF order and fails on any active drive before intended RF TX. They include unguarded and init-level-only controls that reproduce contention. Build verification also checks that the actual ELF links the wrapper and that the upstream RMT call resolves to it. Oscilloscope verification at cold boot and under RF traffic remains a hardware acceptance test.

The same package uses [`rf_radio_handoff.h`](../../include/rf_radio_handoff.h) for runtime transitions. Before each transmission, the host releases GDO0, writes and reads back `IOCFG0=0x2E` (Hi-Z), requests IDLE and requires two IDLE `MARCSTATE` reads. Only then does it drive LOW, which avoids an unwanted OOK carrier during TX entry. It requests TX and requires two TX status reads plus retained Hi-Z configuration before the script may invoke an RMT waveform. A failed check releases the line, latches a fault and skips the entire waveform. The helper uses the existing CC1101 SPI delegate and its shared-bus transaction lock; status reads use command `0xF5`, including the required burst-read bit.

After a completed waveform, the helper requests and verifies IDLE, releases GDO0, checks the retained Hi-Z configuration, and verifies RX before capture resumes. The GDO2 receive output is unchanged. The CC1101 source is hash-pinned because its TX entry must not rewrite `IOCFG0`; configuration rejects `cc1101.gdo0_pin` and packet mode, which would take ownership of the same GPIO. Fault injection in the actual YAML scheduler verifies failed Hi-Z writes, IDLE/TX entry, inconsistent status reads, and failed IDLE/RX return. Cold boot and RX/IDLE/TX transitions still require oscilloscope checks on assembled hardware.

The [2026.10 compatibility review](ESPHOME-2026.10.md) records the source changes and retained SDK guards.
