# SMLIGHT Thread and Home Assistant compatibility review

Reviewed 2026-10-17. This is a source review, not a test of an SMLIGHT unit. The comparison uses the current MC1 software contract and the compiled compact S3-Nano candidate; it does not declare either carrier physically qualified.

**Keep the local S3 border-router architecture for the complete hub.** SMLIGHT's newer products validate that general division of work: an Ethernet host and separate Zigbee/Thread radios. Their useful lessons are management, diagnostics and recovery. Replacing the complete hub with a stock SLZB changes the active Bluetooth and peripheral contract. Moving our H2 radio behind a remote TCP bridge would introduce a failure boundary we currently avoid.

## Four configurations that must not be combined on paper

- **Classic/non-U SLZB with remote OTBR:** the radio's serial stream goes to an OTBR process on HA/Linux, over USB or TCP. Simultaneous Zigbee needs another physical radio. Native BLE features from newer SLZB-OS builds must not be attributed to this configuration.
- **SLZB-MRxU/Ultima with native SLZB-OS:** the S3 runs local OTBR; HA uses its REST endpoint. A second suitable radio can run Zigbee independently. Native BLE forwards advertisements but cannot make active BLE connections. Local OTBR is still described as beta.
- **Official SLZB ESPHome alternative:** active BLE is enabled, but the reviewed image exports radio UARTs through `stream_server`; it does not contain a local OTBR implementation. Thread therefore needs an external OTBR host. This replaces the core firmware; it is not an ESPHome service installed alongside SLZB-OS.
- **Our complete S3-Nano candidate:** local OTBR with H2 RCP; dedicated MG24 Ember NCP; three active BLE connections configured; ZAC93, CC1101, LD2450 and BME680 interfaces retained. Compilation establishes configuration/build compatibility. Concurrent operation, RF performance and recovery still require the assembled hardware.

Sources: [SMLIGHT's two Thread modes](https://smlight.tech/support/manuals/books/slzb-06xmrxmrxuultima-series/page/thread-setup-network-and-usb-connection), [native BLE requirements](https://smlight.tech/support/manuals/books/slzb-os/page/bluetooth-low-energy), [pinned official ESPHome source](https://github.com/smlight-tech/slzb-esphome/tree/3397f6ffe7b0a58cf1546c8293bfa644235a9769), [our full profile](../../../../firmware/module-carrier/README.md), [compact build evidence](../compact-s3/firmware/README.md).

The U suffix and the number of radios are different properties. A single-radio 06xU cannot dedicate that one radio to both Zigbee and Thread simultaneously. The MR5U's two MG24 radios are an especially close architectural comparison. MRW10(U), with a Zigbee/Thread radio plus Z-Wave, must not be counted as two independent Zigbee/Thread radios. Likewise, marketing totals that include Wi-Fi and Bluetooth do not describe the number of independent 802.15.4 networks. [SMLIGHT family overview](https://smlight.tech/support/manuals/books/slzb-06xmrxmrxuultima-series/page/slzb-series-overview), [MRxU model table](https://smlight.tech/products/slzb-mrxu).

## What runs where

An RCP provides the lower radio/MAC functions; its host runs the Thread stack and talks Spinel. A border router forwards IPv6 between Thread and the LAN. Neither role is the Matter controller. [OpenThread co-processor architecture](https://openthread.io/platforms/co-processor).

HA still runs its Matter controller/server when using either SMLIGHT mode or our hub. Thread credentials and Matter fabric credentials are separate state. In HA's documented commissioning flow the phone supplies Bluetooth proximity; adding a BLE proxy does not replace that flow. IPv6 and discovery must work on the LAN regardless of where OTBR runs. [HA Matter](https://www.home-assistant.io/integrations/matter/).

For local SLZB OTBR, the documented default integration URL is `http://DEVICE:8080`. Our endpoint is `http://DEVICE:8081`. HA's OTBR integration calls this HTTP REST service; it is not the Matter data tunnel. The SMLIGHT management integration is a separate integration for device monitoring/control. [SMLIGHT Thread setup](https://smlight.tech/support/manuals/books/slzb-06xmrxmrxuultima-series/page/thread-setup-network-and-usb-connection), [HA OTBR](https://www.home-assistant.io/integrations/otbr/), [HA SMLIGHT](https://www.home-assistant.io/integrations/smlight/).

The remote-RCP distinction has a practical consequence: HA's own OTBR app warns that TCP latency/loss violates assumptions of its reliable UART/SPI link. After network failure, stale routes can remain for up to 30 minutes, even with another working border router. Keeping host and RCP together avoids that particular split, although it does not automatically prove good Ethernet reconnection. [HA OTBR app documentation](https://github.com/home-assistant/addons/blob/master/openthread_border_router/DOCS.md).

## Versions and scope of evidence

- Native SLZB-OS BLE requires **3.3.3.dev7 or newer** and **HA 2026.8 or newer**; advertisement forwarding uses UDP 5050. Active scanning is not an active GATT connection. [BLE manual](https://smlight.tech/support/manuals/books/slzb-os/page/bluetooth-low-energy).
- The software landing page advertises **3.3.1**, while the reviewed detailed changelog reaches **3.4.3.dev1**. These are not interchangeable declarations of the currently installed or recommended stable version. [Software page](https://smlight.tech/software/slzb-os), [changelog](https://smlight.tech/support/manuals/books/slzb-os/page/changelog-slzb-os).
- Relevant development milestones: **3.3.3.dev1** labels on-device OTBR beta and adds experimental configuration backup; **3.3.8.dev3** adds a separate REST IP whitelist; **3.3.8.dev7** fixes IPv6/OMR forwarding after link loss; **3.4.3.dev1** adds graceful OTBR stop and further NAT64, mDNS and RCP fixes. Vendor fixes are evidence of test cases to reproduce, not independent reliability measurements. [Changelog](https://smlight.tech/support/manuals/books/slzb-os/page/changelog-slzb-os).
- The inspected HA OTBR app configuration declares **3.3.0** and HA minimum **2025.7.0**. Its default hardware flow-control setting is true, whereas SMLIGHT's example RCP setup specifies false at 460800 baud. Match the selected radio image rather than copying defaults. [HA app configuration](https://github.com/home-assistant/addons/blob/master/openthread_border_router/config.yaml), [SMLIGHT setup](https://smlight.tech/support/manuals/books/slzb-06xmrxmrxuultima-series/page/thread-setup-network-and-usb-connection).
- The official alternative ESPHome code reviewed is commit **3397f6ffe7b0a58cf1546c8293bfa644235a9769**. Our full build uses **ESPHome 2026.9.1 / ESP-IDF 5.5.5**. No model-specific current SMLIGHT RCP image/version pair was independently verified. Before a trial, record the exact device revision, core version, radio image/version/hash, role, baud and flow control; a core OS version alone does not identify that contract.

## Backup, migration and REST acceptance

Preserve four distinct kinds of state; a core-firmware backup does not by itself prove coverage of all four:

1. **Thread dataset:** retain a private export of the active operational dataset and test import into a spare/reset device. Confirm network identity after reboot. HA's preferred-network setting and phone credential sync must refer to that same network; matching display names are insufficient. [HA Thread](https://www.home-assistant.io/integrations/thread/).
2. **Matter controller state:** back up the Matter server's data as well as HA configuration. Replacing a border router does not replace or recover the controller's fabric credentials. HA's server migration instructions explicitly call for an app backup before migration. [Matter server migration FAQ](https://github.com/home-assistant/addons/blob/master/matter_server/MIGRATION_FAQ.md).
3. **Zigbee coordinator and host state:** retain the existing ZHA or Zigbee2MQTT backup path. ZHA supports migration inside ZHA across supported Silicon Labs/TI/ConBee families. That is not a promise of ZHA-to-Zigbee2MQTT migration. [HA ZHA backup/migration](https://www.home-assistant.io/integrations/zha/).
4. **Hub configuration and other networks:** separately preserve RF payloads/topics, ESPHome credentials, Z-Wave state, hardware pin maps and exact firmware artifacts. Do not infer their inclusion in an SLZB-OS settings export.

For Zigbee2MQTT, normal backup/restore currently covers `ember` and `zstack`; cross-family migration is not officially guaranteed. Preserving Ember in both our MG24 and an appropriate SLZB radio avoids an unnecessary family change, but still requires a restore test. [Zigbee2MQTT migration FAQ](https://www.zigbee2mqtt.io/guide/faq/).

SLZB's onboard **Zigbee Hub** mode is another application with its own converter/database behavior; it is not the ZHA/Zigbee2MQTT coordinator bridge. Its EFR32 backup feature appeared in **3.4.1.dev1**. The EFR32 firmware dialog gained default-enabled NVM clearing in **3.3.3.dev4**: inspect that option before touching an established network. [Changelog](https://smlight.tech/support/manuals/books/slzb-os/page/changelog-slzb-os).

Our REST implementation already has a useful strength: a loopback test compiles the actual C handlers/parser and drives them with `python-otbr-api` **3.0.0**. It checks unknown-path HTTP 404, client flavor detection and dataset fields. Keep those tests. They do not prove flash persistence, actual HA discovery, or IPv6 routing on the board. Extend acceptance to dataset export/import, cold reboot, IPv6 address changes, OMR routes and mDNS after link loss. [Existing REST contract and limits](../../../../firmware/low-power/README.md#rest-regression-check).

## Changes worth adopting

**Prioritize recovery and observability.** Exercise missing, stale and repeatedly resetting H2 RCP firmware; a switch reboot; DHCP/address renewal; and sustained concurrent radio traffic. Our wrapper launches once after Ethernet connects and delegates substantial behavior to ESP-IDF. Inspect that recovery behavior before adding another reset loop. Report internal heap/PSRAM margins, task stack margin, RCP resets and stream stalls independently from the whole-hub watchdog. A radio problem should not automatically erase its network or repeatedly reset every protocol.

**Separate endpoint protection.** SLZB exposes web authentication and socket restrictions; recent builds additionally distinguish OTBR REST access. Our encrypted ESPHome API does not secure the separate unauthenticated REST 8081 or Ember TCP 6638 endpoints. Use restricted automation-network access and consider explicit endpoint ACLs; preserve required IPv6/multicast paths. Never put datasets into screenshots or published diagnostics. [SMLIGHT security](https://smlight.tech/support/manuals/books/slzb-os/page/security), [our documented endpoint behavior](../../../../firmware/low-power/README.md#home-assistant-and-local-network).

**Keep independent recovery access.** SMLIGHT documents button-forced USB flashing and return from ESPHome to SLZB-OS. We should retain physical boot/recovery access and versioned images, then test interrupted updates and safe fallback. Do not make all recovery depend on an operational LAN or mistake OS rollback for radio-NVM rollback. [Official ESPHome installation/recovery](https://smlight.tech/support/manuals/books/slzb-06xmrxmrxuultima-series/page/esphome-firmware-for-ultima-and-xu-series).

A finished MRxU is a reasonable evaluation candidate if the desired appliance is specifically Zigbee plus Thread. Ultima's optional Z-Wave/RF support narrows the gap, but does not establish parity for our active BLE, radar/environment interfaces or RF message contracts. For the complete ceiling hub, preserve the selected architecture and adopt these operational improvements before another PCB change. No purchase, firmware flash, network migration or active source modification was performed for this review.
